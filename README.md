PrismatiXEngine combines typed content contracts and deterministic Story execution with a native Player and PreviewHost. Story authors work through the project-local CLI; building the C++ engine is a separate contributor workflow.

## Make your first game in five steps

You need Node.js 20 or newer and the released PrismatiX runtime bundle for your platform. You do not need CMake, vcpkg, an engine checkout, or a globally installed PrismatiX command.

1. Install the CLI in an empty authoring directory.

   ```bash
   npm init -y
   npm install --save-dev @prismatix/cli
   ```

2. Create the playable starter.

   ```bash
   npx prismatix create first-game --name "First Light" --locale en
   cd first-game
   ```

3. Change the welcome line in `Story/main.pxstory`.

   ```pxstory
   [id main.welcome]
   The station lights came on one by one.
   ```

4. Preview it. Saving a dependency reports source diagnostics and updates Preview.

   ```bash
   npx prismatix dev
   ```

5. Build a portable distribution under `dist/<project-id>/`.

   ```bash
   npx prismatix build
   ```

Released CLI packages may include the matching native runtime. For a standalone bundle, set `PRISMATIX_RUNTIME_DIR` to its install prefix or pass `--runtime <prefix>` to `dev` and `build`. See [Build your first PrismatiX game](docs/getting-started.md) for runtime discovery, `dev --once`, diagnostics, explicit packaging, and the clean-machine release gate.

## What authors get

- `.pxstory` parsing with precise source spans and project-aware validation.
- A default title screen, catalog, locale, and canonical project metadata generated by `create`.
- Native Preview with dependency watching and safe Runtime IR patch/restart behavior.
- Declarative JSON or React-free TSX UI, typed Actions, styles, animation, and behavior graphs.
- Sandboxed JavaScript extensions without Node.js, filesystem, process, network, dynamic evaluation, wall-clock, or unrestricted random APIs.
- Offline-compiled custom Stage shaders and portable native Player packages.

The build-time `@prismatix/authoring-sdk` compiles deterministic Runtime IR and source maps. The optional `@prismatix/runtime` package supplies types and an ergonomic facade for extensions; the shipped game still runs the embedded native QuickJS-NG host.

## Engine contributors

The following dependencies are for people building or changing PrismatiXEngine itself. They are not part of the author quickstart.

- A C++20 compiler: current MSVC, Clang, or GCC.
- CMake 3.21 or newer and Ninja for preset builds.
- SDL3 with Image, TTF, Mixer, and SDL3_shadercross.
- FFmpeg (`libavformat`, `libavcodec`, `libavutil`, `libswscale`, `libswresample`).
- nlohmann-json, spdlog, MbedTLS, zstd, fmt, and the dependencies resolved by the repository presets.

Install the JavaScript toolchain and run all contract, SDK, CLI, docs, and clean-install checks:

```bash
npm ci
npm run check
```

Configure and build a native preset appropriate for your host. On macOS:

```bash
brew install cmake ninja sdl3 sdl3_image sdl3_ttf sdl3_mixer nlohmann-json spdlog mbedtls zstd fmt
cmake --preset macos-debug
cmake --build --preset macos-debug
```

On Windows, the maintained presets include `x64-debug`, `x64-relwithdebinfo`, and `x64-release`:

```powershell
$env:VCPKG_ROOT = "C:\path\to\vcpkg"
# Run from a Visual Studio Developer PowerShell with Ninja on PATH.
cmake --preset x64-debug
cmake --build --preset x64-debug
```

Presets intentionally contain no user-specific Visual Studio, Windows SDK,
Ninja, Homebrew, or vcpkg paths. Windows compiler discovery comes from the
Developer PowerShell environment; `VCPKG_ROOT` selects the dependency
toolchain.

Runtime and test binaries are generated under `out/build/<preset>/PrismatiXEngine/`. Install the redistributable runtime component to a staging prefix before running the real Phase 1 acceptance gate:

```bash
cmake --install out/build/<preset> --prefix out/install/<preset> --component PrismatiXRuntime
PRISMATIX_PHASE1_RUNTIME=out/install/<preset> npm run test:phase1
```

The default `npm test` runs the fast repo-external mock gate. A release is not considered playable until the real runtime gate has also passed; details are in the [getting-started guide](docs/getting-started.md#verify-a-runtime-bundle-release).

## Repository map

```text
PrismatiXEngine/
├── PrismatiXEngine/
│   ├── Applications/       # Player, native Preview, WASM Preview, Packager
│   ├── Engine/             # Runtime, SDK, UI, VN, media, and platform code
│   └── Tests/              # Contracts, integration, acceptance, soak, fuzz
├── Contracts/              # Canonical JSON Schemas and generated lock data
├── packages/
│   ├── authoring-sdk/      # Frontend-neutral authoring compiler
│   └── cli/                # create/dev/validate/build/pack/run tooling
├── runtime-sdk/            # TypeScript extension facade and declarations
├── Samples/                # End-to-end authored projects
└── scripts/                # Contract and release acceptance automation
```

Runtime extensions live under `Content/Extensions/`. Custom Stage shaders use the bounded [`.pxeffect` contract](docs/custom-effects.md); packages contain fingerprinted SPIR-V, DXIL, and MSL artifacts, never author HLSL or a runtime shader compiler. The canonical public C++ UI contract is `Engine/SDK/Ui.h`; the 0.1 `StudioUi` compatibility surface was removed in the 0.2 breaking release.

The [0.2.0 delivery contract](docs/releases/0.2.0.md) defines supported native
shipping targets and required clean-machine/browser gates. Release artifacts
carry the [third-party notice inventory](THIRD_PARTY_NOTICES.md) and
[asset provenance](ASSET_PROVENANCE.json); the Emscripten build is a Studio
Preview, not a web-game distribution.
